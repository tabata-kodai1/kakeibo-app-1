# 要件定義書

## 1. 背景と目的

「今月はこの金額までに抑えたい」と決めていても、実際にいくら使ったかを把握していないと、気づいたときには使いすぎている。レシートや支払い履歴を見返すだけでは、**予算に対してあといくら使えるのか**が分からない。

本アプリは、**決めた予算の範囲内で生活できているかを一目で把握できる**ことを目的とした家計簿 Web アプリケーションである。

想定する利用の流れは次のとおり。

```
  ① 月の予算を決めて登録する      →「9月は80,000円まで」
  ② 支払いのたびに記録する        →「9/25 食費 1,280円」
  ③ 残額を確認する                →「残り27,700円」 ★ここが最重要
  ④ 内訳を見て使いすぎに気づく    →「食費が32,100円…多いな」
```

**③の「あといくら使えるか」に答えること**が、このアプリの中心的な価値である。単なる記録の保管庫ではない。

初級者最終課題として、以下の開発プロセスを実践することも目的に含む。

- 要件定義 → 技術選定 → 設計 → 実装 → デプロイ
- GitHub Issue / PR ベースの開発運用
- Terraform による AWS へのインフラ構築とデプロイ

## 2. スコープ

### 2.1 対象範囲（作るもの）

| 区分 | 内容 |
| --- | --- |
| 予算管理 | 月ごとの予算設定、予算に対する使用額・残額・進捗の表示 |
| 収支の記録 | 追加、編集、削除、一括更新 |
| 閲覧 | 月別の明細一覧、月の切り替え、カテゴリ別の集計、検索・絞り込み |
| カテゴリ | あらかじめ用意した固定カテゴリから選択する |
| 画面 | 単一ページのダッシュボード + 入力モーダル |
| データ永続化 | 記録したデータを永続化し、再起動後も保持する |
| デプロイ | クラウド環境にデプロイし、ブラウザから利用できる状態にする |

詳細な機能定義は [features.md](./features.md) を参照。

### 2.2 対象外（作らないもの）

家計簿アプリで考えられる機能を洗い出したうえで、**上記の目的に寄与するか**を基準に取捨選択した。以下は検討した結果、意図的に対象外としたもの。

#### 目的に寄与しないため外したもの

| 機能 | 外した理由 |
| --- | --- |
| **手動の並び替え（ドラッグ&ドロップ）** | 家計簿の明細に恣意的な順序を付ける意味がなく、日付順で見るのが自然。さらに、絞り込み中は全体の順序が壊れるため無効化せざるを得ず、「なぜ今使えないのか」がユーザーに伝わらない。UX を損なう副作用のほうが大きいと判断した |
| **列ソート（日付順・金額順）** | 月別表示とカテゴリ別集計があれば、目的である「予算に対する残額の把握」は達成できる。優先度が低い |
| カレンダー表示 | 明細一覧と役割が重複する |

#### 価値はあるが、工数を優先して外したもの

| 機能 | 外した理由 |
| --- | --- |
| **カテゴリ別の予算設定** | 月全体の予算だけで「あといくら使えるか」には答えられる。カテゴリ別にすると設定画面とデータ構造が複雑になるため、今回は月全体のみとした |
| **グラフによる可視化**（円グラフ・推移） | カテゴリ別集計を数値と割合の表で出せば、内訳の把握はできる。グラフ描画ライブラリの習得コストを避けた |
| **前月との比較** | あると有用だが、残額の把握という中心的価値には直接寄与しない |
| **カテゴリの追加・編集・削除** | 固定カテゴリ13件で日常的な記録はカバーできる。管理画面の追加コストに見合わない |
| **定期支出の自動登録**（家賃・サブスク） | 入力の手間は減るが、自動生成のタイミング制御など考慮点が多い |
| **よく使う入力のテンプレート** | 同上。入力補助は今回のスコープ外とする |
| CSV の入出力 | 他ツールとの連携は今回の目的に含まれない |

#### 今回の前提により外したもの

| 機能 | 外した理由 |
| --- | --- |
| ユーザー認証・ログイン | **単一ユーザー前提**。認証は機能を1つ足すのではなく全 API に影響する横断的な要件であり、CRUD とデプロイの完走を優先した |
| 複数ユーザーでのデータ分離、家族共有 | 同上 |
| 複数通貨対応 | 日本円のみとする |
| レシート画像の読み取り（OCR）、画像添付 | 実装コストが大きく、目的への寄与が限定的 |
| 銀行・カード明細の自動取り込み | 外部サービス連携は本課題の範囲を超える |
| 支払い方法（現金/カード）の記録、タグ付け | 分類軸を増やすと入力と集計が複雑になる |
| スマートフォンアプリ、通知機能 | 対象外 |

## 3. 用語定義

| 用語 | 説明 |
| --- | --- |
| 収支レコード（レコード） | 1 件の収入または支出の記録。日付・カテゴリ・金額・メモを持つ |
| カテゴリ | レコードの分類。「食費」「給与」など。収入用と支出用がある |
| 収支区分 | カテゴリが収入（INCOME）か支出（EXPENSE）かを表す種別 |
| 予算 | その月に使ってよい支出の上限額。月ごとに 1 つ設定する |
| 残額 | 予算からその月の支出合計を引いた額。マイナスなら予算超過 |
| 対象月 | 画面が現在表示している年月。前月／翌月に切り替えられる |
| 選択モード | 明細一覧で複数件を選択して一括操作を行うための表示状態 |

## 4. 利用者と利用シーン

- 利用者: 予算を決めて家計を管理したい個人 1 名
- 利用シーン:
  - 月初に、その月の予算を登録する
  - 買い物や給与の受け取りがあったとき、その場でレコードを追加する
  - 買い物の前に残額を確認し、使ってよい金額を判断する
  - 内訳を見て、どのカテゴリで使いすぎているかを把握する
  - レシートをまとめて入力した後、日付が今日になっている複数件をまとめて正しい日付に直す

## 5. 非機能要件

本アプリは **単一ユーザー・学習用途** であり、常時稼働や多人数利用を前提としない。代表的な要件は次のとおり。

| 分類 | 要件 |
| --- | --- |
| 対応ブラウザ・画面幅 | 最新版の Google Chrome（PC）、1280px 以上を基準とする |
| 性能 | レコード 1,000 件程度で、主要な取得 API のレスポンスが 1 秒以内 |
| データ永続化 | PostgreSQL に保存し、アプリ再起動後もデータが保持される |
| 可用性 | 常時稼働は要件としない。単一 EC2 インスタンス構成で可 |
| セキュリティ | 認証がないため、接続元 IP とネットワークの制限で公開範囲を絞る |
| 構成管理 | インフラは Terraform でコード化し、`terraform destroy` で撤去できる |

**要件 ID（N-01〜N-40）と各項目の確認方法、対象外とした非機能要件は [non-functional.md](./non-functional.md) で定義する。**

## 6. 前提条件・制約

### 6.1 金額と日付

- 通貨は日本円のみ、金額は小数を扱わない整数とする
- 時刻は扱わず、レコードは日付（年月日）単位で記録する
- タイムゾーンは Asia/Tokyo を前提とする。**「当月」の判定はサーバーの Asia/Tokyo における日付による**（ブラウザ側の時刻設定には依存しない）
- **未来日付のレコードを登録できる**。翌月に切り替えて予定を記録する使い方を許容するため、上限日のチェックは行わない
- 1 件あたりの金額の上限は 9,999,999 円、予算の上限は 99,999,999 円とする（予算は 1 か月の合計を受け止めるため 1 桁多く取る）

### 6.2 予算

- 予算の対象は**支出のみ**とする（収入は残額の計算に含めない）
- 予算が未設定の月でも、明細の記録と閲覧はできる
- **予算 0 円と予算未設定は別の状態として扱う。** 0 円は「今月は使わない」という設定であり、支出があれば超過として扱う。未設定は判断の材料がない状態として、残額・使用率を表示しない
- **一度設定した予算を「未設定」に戻す手段は持たない。** 予算を削除する API・操作は用意せず、変更は上書きのみとする。未設定は月の初期状態を表すもので、そこへ戻す必要が生じるのは誤って登録した直後に限られ、正しい金額で上書きすれば実害がないため。この割り切りにより API を 1 本増やさずに済む

### 6.3 カテゴリ

- カテゴリはアプリが用意する固定の 13 種類とし、追加・変更・削除の機能は持たない
- **カテゴリの収支区分をまたぐ変更はできない。** 支出のレコードを収入カテゴリに付け替えることは、編集・一括更新のいずれでも許可しない（区分が変わると残額が大きく動くのに、画面上は「カテゴリを直しただけ」に見えるため）

| 収支区分 | カテゴリ |
| --- | --- |
| 支出（EXPENSE） | 食費 / 日用品 / 交通費 / 住居費 / 水道光熱費 / 通信費 / 娯楽費 / 医療費 / その他 |
| 収入（INCOME） | 給与 / 賞与 / 副収入 / その他収入 |

### 6.4 データの扱い

- **重複チェックは行わない。** 同じ日・同じカテゴリ・同じ金額のレコードを複数登録できる（同日に同じ店で 2 回買うことがあるため）
- **削除は物理削除とし、復元できない。** ゴミ箱や取り消し操作は持たないため、削除前に確認ダイアログを挟む
- **データの保持期間は設けない。** 古いレコードの自動削除やアーカイブは行わず、登録したものは残り続ける
- **同時編集の競合検出は行わない。** 単一ユーザー前提のため、複数タブで同じデータを開いた場合は**最後に保存した内容が有効**になる（先の変更は警告なく上書きされる）
- 一括操作の対象は 1 回あたり 500 件までとする

### 6.5 課題として指定された技術

以下は本課題であらかじめ指定されているもので、要件から導いた選択ではない。前提条件として扱う。

| 項目 | 指定内容 |
| --- | --- |
| データベース | PostgreSQL |
| インフラ | AWS（EC2 + RDS + S3） |
| 構成管理 | Terraform によるコード化 |

これ以外の技術（言語・フレームワーク・テスト・CI など）は要件から選定する。選定結果と理由は [tech-stack.md](./tech-stack.md) で確定する。
