# design-audit

設計書と実装のずれを洗い出し、直す。[N-18](../../../docs/non-functional.md#保守性運用) の「設計書と実装を突き合わせ、差異が 0 件であること」の確認にあたる。

ツール（RuboCop・RSpec など）の実行は `quality-check` の役目。**このスキルは、まず `quality-check` を実行して全部通ることを確かめてから始める。** テストが落ちたままでは、実装の状態を正しく読めない。

## 大原則

**設計書が正。** ずれを見つけたら、次のどちらかを判断する。

| 判断 | やること |
| --- | --- |
| 実装が間違っている（原則） | 実装を直す。設計書は触らない |
| 設計書が誤っている・設計を変える | **先に設計書を更新してから**実装する。実装だけ先に変えて、設計書を後から合わせることはしない |

設計書に**定めがない**挙動（設計の空白）は、ずれではない。実装が正しいと決めつけず、「定める」か「対象外と明記する」かをユーザーに確認して決める。**設計書の書き換えは、黙って行わない。** 方向が自明でないものは、理由を添えてユーザーに尋ねる。

## 何を何と比べるか

読むだけで「合っている」と判断しない。API は実際に `curl` で叩き、画面はコードのうえで条件を 1 つずつ辿る。

| 設計書 | 比べる相手 |
| --- | --- |
| `docs/requirements.md` の対象範囲・前提条件（6.x）・用語 | 実装全体。とくに 6.1 金額と日付、6.2 予算（0 円と未設定の区別、削除しない）、6.3 カテゴリ（13 種・区分をまたぐ変更の禁止）、6.4 データの扱い（重複チェックなし、物理削除、同時編集の検出なし、500 件） |
| `docs/requirements.md` の対象外（2.2）と `CLAUDE.md` の「やらないこと」 | 追加してはいけないものが混ざっていないか。`Gemfile`・`package.json` の依存、ルート、画面の要素を見る |
| `docs/features.md` の API 仕様・バリデーション・エラーレスポンス | `backend/config/routes.rb`、`app/controllers/api/`、`app/models/`、`app/views/api/**/*.jbuilder`。動作中の API を叩いて実際の JSON・ステータスを確かめる |
| `docs/features.md` の受け入れ条件（F-01〜F-09） | `backend/spec/requests/`。**条件 1 つにつき `it` が 1 つ以上あるか。** 画面側の条件は下の画面設計の行で確かめる |
| `docs/screens.md`（S-01〜S-04、エラーの表示、送信中の扱い、更新後の画面） | `frontend/src/App.vue` と `components/`、`utils/`、`api/`。表示文言・件数表示の判定・選択モードの扱い・モーダルの挙動を 1 項目ずつ |
| `docs/database.md` | `backend/db/schema.rb`（列・型・制約・インデックス・照合順序）、`db/seeds.rb`（13 件・再実行しても重複しない） |
| `docs/non-functional.md`（N-01〜N-40）の各「確認方法」 | 確認方法に書かれたとおりに実行する。現時点で確認できないもの（AWS、ブラウザ操作）は分けて記録する |
| `docs/tech-stack.md`（採用技術一覧、設定値の扱い、環境変数） | `Gemfile.lock`、`package.json`、`.ruby-version`、`docker-compose.yml`、`.github/workflows/ci.yml`。バージョン方針と実際が合っているか |
| `docs/plan.md` の各フェーズの完了条件 | 完了済みのフェーズの条件を 1 つずつ。ブラウザ操作が要るものは、確認していないと明記する |
| `docs/mockups/*.html` | screens.md の本文と、モックアップの表示（設計書にない注記・要素がないか）。モックアップだけにある要素は、設計書の本文に合わせて消すか、設計に加えるかをユーザーに確認する |
| `CLAUDE.md` の「実装上の注意」 | 該当するコード（`update_all` の事前検証、`delete_all`、月の範囲比較、SQL 集計、残額の計算、`category_type` の列名など） |

## 進め方

1. `quality-check` を実行し、全部 PASS であることを確かめる。画面に関わるなら、あわせて下の「ブラウザで操作して確認する」を実行する
2. 上の表の行ごとに、設計書を上から読み、確認できる項目を 1 つずつ実装側と照らす
3. ずれ・空白を見つけたら、表に記録する（項目 / 設計書の記述 / 実装の状態 / 判断: 実装を直す・設計を変える・定めを足す）
4. **結果を GitHub Issue に記録する。** 確認した対象と方法、差異なしだった項目、未決の項目、確認していない項目を分けて書く
5. 直す。1 件 = 1 Issue = 1 PR。**main に直接 push しない。PR を通し、CI が緑になってからマージする**
   - 実装を直すものは、設計書の記述をそのままリクエストスペックの `it` に落としてから直す
   - 設計を変えるものは、なぜ実装ではなく設計を変えるのかを PR 本文に書く。設計書の更新は実装より先
6. 直したあとは `quality-check` を再実行し、対象の項目を確かめ直す。**差異が 0 件になったら Issue を閉じる**

## ブラウザで操作して確認する

画面の挙動は、コードを読むだけでは確かめきれない。実際に、#64 の監査で、コードを読んで「差異なし」とした画面に、操作して初めて分かる不具合があった（モーダルを開いたとき、フォーカスが最初の入力欄ではなく「×」に当たっていた。N-21、#71）。**画面（S-01〜S-04）に関わる監査では、次を実行する。**

```
bash .claude/skills/design-audit/browser-check.sh
```

Docker・Node.js・Google Chrome が必要。約 2 分かかる。

- 専用の DB（`kakeibo_e2e`）・専用のポート（API 3001、Vite 5174）で**隔離環境**を立て、Chrome を Playwright から操作し、終わったら片付ける。**開発用の DB・サーバー（3000・5173）には触れない**（データも消さない）
- `playwright-core` は一時ディレクトリに入れる。**リポジトリの `package.json`・CI には入れない**（CLAUDE.md の「テスト対象は API のリクエストスペック。フロントエンドは手動確認」に合わせる。自動操作は、監査で確かめるための道具で、CI の検査ではない）
- 確認する内容（98 項目）: plan.md フェーズ5の完了条件（予算設定 → 追加 → 残額が減る → 削除 → 戻る、月切替の連動、絞り込み中のサマリー不変、期間検索の注記、バリデーションの表示、API 停止時のバナー、連打、10 秒のタイムアウト）、選択モードと一括更新・一括削除、確認ダイアログ、モーダルの共通挙動（Esc・背景・開き直し・フォーカス）、404 のときの表示、1280px での横スクロール
- 画面の仕様を変えたら、`browser-check.mjs` の期待値も同じ PR で直す。**このスクリプトも設計書が正**で、失敗したときは、まず実装が設計書とずれていないかを疑う（期待値を実装に合わせない）
- 失敗した項目は、スクリーンショット（出力の最後に置き場所が出る）と設計書を見比べて、「実装を直す」か「設計を変える」かを判断する

**自動では確認できないもの:** 人の目での見た目（色の見分けやすさ、レイアウトの崩れ）、Chrome 以外のブラウザ、AWS 上の動作。これらは、ユーザーに実際に操作してもらう。

## 結果に必ず書くこと

- **自動では確認できなかったもの**（人の目での見た目、AWS 上の設定など）は、確認していないと明記する。コードを読んだだけの項目を「動作確認した」と書かない
- 差異なしと判断した項目には、確認の方法（スペックを読んだ、curl で叩いた、コードを読んだ）を添える

## 注意

- 実装で決めたのに設計書にない判断が出たら、PR 本文だけでなく `docs/` にも書く
- 「やらないこと」（`CLAUDE.md`）に該当する機能は、気を利かせて追加しない
